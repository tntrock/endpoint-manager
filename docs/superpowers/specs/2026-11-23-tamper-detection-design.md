# 偵測本機資料竄改

日期：2026-11-23
來源：`docs/roadmap.md` 第 3 項。取代先前只靠序號缺口的草稿（只擋得住粗糙的竄改）。

## 1. 目標與前提

**目標是「偵測」，不是「防止」。**電腦上有管理員權限的人能控制那台電腦上的一切：改檔案、停服務、清紀錄、改 Agent 本身。所以單靠 Agent 自己說的話，永遠可以被假造。

這份規格用兩個方向補強：

1. **縮短能動手的時間**：事件發生後幾秒內就送到伺服器。送到之後本機怎麼改都沒用。想不留紀錄，就得在事情發生**之前**先把 Agent 停掉。
2. **加上不是從那台電腦來的證據**：「Agent 被停掉」本身會被看到——作業系統有紀錄，交換器也看得到這台電腦還在網路上卻沒報到。

### 1.1 分層

| 層 | 證據來源 | 能抓到什麼 | 偽造難度 |
|---|---|---|---|
| A. 事件立即上傳 | Agent | 縮短竄改的時間窗；之後的層都靠它即時送出 | — |
| B. Agent 的啟動與停止 | Agent、作業系統 | 服務被停止、被強制結束、被改成停用、非正常結束 | 中：要先停掉 Agent，而停掉本身會被 C 看到 |
| C. 網路端交叉比對 | 交換器、路由器 | Agent 不報到但電腦還在網路上；IP 被別的 MAC 使用；同一個 MAC 同時出現在兩個埠 | 高：要能控制網路設備 |
| D. 作業系統紀錄被清除 | 作業系統（Windows） | 安全性、系統紀錄被清除 | 中：清除這個動作本身會留下紀錄 |
| E. 序號缺口、日誌重建 | Agent 日誌 | 刪掉日誌裡的幾筆事件、整個刪掉重來 | 低：最基本的一層 |

### 1.2 偵測不到的情況（README 要寫）

- 有權限的人在 Agent 啟動前就改好設定，之後一直維持：沒有「變化」可以記錄。
- 同時控制電腦與網路設備（例如把電腦接到沒有登錄的交換器）：C 層看不到。
- Linux 的系統紀錄被清除：journald 沒有像 Windows 1102 這樣可靠的「清除」事件，只做 B 層的服務停止紀錄。
- 修改 Agent 執行檔讓它回報假資料：要靠 TPM 遠端證明，仍留待之後。

**不做雜湊鏈**：鏈結的雜湊沒有本機拿不到的密鑰，有管理員權限的人可以整條重算。事件即時上傳後，已上傳的部分本來就改不了，雜湊鏈多不了保護。

## 2. 發現（finding）

各層偵測到的結果統一存成「發現」，後台用同一套方式顯示與處理。

### 2.1 種類

| 種類 | 來源 | 嚴重度 | 說明 |
|---|---|---|---|
| `agent_stopped` | B | 中 | Agent 服務被停止（正常停止，有原因） |
| `agent_killed` | B | 高 | Agent 被強制結束或非正常結束（沒有正常停止的紀錄） |
| `agent_disabled` | B | 高 | Agent 服務被改成「停用」或「手動」 |
| `log_cleared` | D | 高 | Windows 安全性或系統紀錄被清除 |
| `silent_on_network` | C | 高 | Agent 沒報到，但交換器上還看得到這台電腦 |
| `ip_conflict` | C | 中 | Agent 回報的 IP，路由器的 ARP 表卻對到別的 MAC |
| `mac_duplicate` | C | 中 | 這台電腦的 MAC 同時出現在兩個端點埠 |
| `journal_gap` | E | 中 | 事件序號不連續，Agent 沒有說明原因 |
| `journal_rebuilt` | E | 中 | 30 天內事件日誌重建 3 次以上 |

Agent 正常升級時會重新啟動，`agent_stopped` 會帶 `reason: "upgrade"`，**不產生發現**。重新開機也一樣（`reason: "shutdown"`）。

### 2.2 資料表

```
device_findings
  id
  device_id
  kind                  上表的種類
  severity              high / medium
  started_at            開始時間（例如 Agent 被停掉的時間）
  ended_at              持續型的發現何時結束（silent_on_network 等）；一次性的與 started_at 相同
  detail JSONB          依種類不同：清除者帳號、交換器與埠、缺的序號範圍……
  source                agent / network / server
  acknowledged_at, acknowledged_by, ack_note
  created_at
```

- 持續型的發現（`silent_on_network`、`ip_conflict`、`mac_duplicate`）開啟時 `ended_at` 是空的，條件消失時補上。
- 同一台裝置、同一種類、還沒結束的發現只有一筆（部分唯一索引）。

### 2.3 確認

管理員看過、確定沒問題的發現可以按「確認」，填寫說明（例如「IT 換網卡」），寫入稽核記錄。已確認的不再列在「需要處理」，但時間軸與發現清單仍然看得到。

**權限**：能管理這台裝置的人才能確認。

## 3. A 層：事件立即上傳

現在網卡變化會讓 Agent 提早報到（等 10 秒合併），事件跟著報到一起送出。改成獨立、更快的上傳：

### 3.1 Agent

- 新的 `POST /v1/events`，內容與報到裡的 `journal_id`、`events` 相同，回應 `events_ack`。
- 日誌新增事件時通知上傳工作：**等 1 秒**合併同時發生的事件後送出。
- 送失敗照現有的退避重試。報到時仍然附帶沒確認的事件，當作備援。
- 伺服器在報到回應裡宣告 `supports_event_push`，Agent 看到才用新的端點；舊版伺服器照舊跟著報到送。

### 3.2 伺服器

- 新端點與報到共用 `events::ingest`，用裝置憑證驗證，限制每批最多 500 筆（與報到相同）。
- 速率限制：每台裝置每秒最多 2 次，超過回 429，Agent 退避。

## 4. B 層：Agent 的啟動與停止

### 4.1 新的事件

| 事件 | 時機 | 資料 |
|---|---|---|
| `agent.started` | Agent 啟動 | `version`、`clean`（上次是否正常結束）、`last_alive`（上次最後活著的時間） |
| `agent.stopping` | 收到停止要求 | `reason`：`service_stop`、`shutdown`、`upgrade` |
| `agent.service_config` | 服務的啟動類型改變 | `from`、`to`（`auto`、`manual`、`disabled`） |
| `os.service_stopped` | Windows 7036／7034（只看 Agent 自己的服務） | `event_id`、`user`（系統紀錄記得到時） |

**正常結束標記**：狀態目錄的 `alive` 檔案每 30 秒更新一次時間；正常停止時寫入 `clean`。下次啟動讀到沒有 `clean` 就是非正常結束，`last_alive` 就是最後活著的時間。

**停止前送出**：收到停止要求時記 `agent.stopping`，最多等 3 秒送出（Windows 服務停止有時間限制），送不出去就留在日誌，下次啟動補送。

**啟動類型**：每次報到檢查一次 Agent 服務的啟動類型（Windows：服務設定；Linux：`systemctl is-enabled`），改變時記事件。

### 4.2 Windows 系統紀錄

Agent 以系統服務身分訂閱事件紀錄（`EvtSubscribe`），只收下列事件：

| 紀錄 | 事件 ID | 意義 | 篩選 |
|---|---|---|---|
| 系統 | 7036 | 服務進入停止狀態 | 只看 Agent 自己的服務 |
| 系統 | 7034 | 服務意外終止 | 同上 |
| 系統 | 7040 | 服務啟動類型被改變 | 同上 |
| 安全性 | 1102 | 稽核紀錄被清除 | 全部 |
| 系統 | 104 | 系統紀錄被清除 | 全部 |

- Agent 停止期間發生的事件，啟動時從上次讀到的位置（書籤存在狀態目錄）補讀。
- 1102、104 記成 `os.log_cleared`，資料包含紀錄名稱與清除者帳號。

### 4.3 Linux

- 啟動時讀 Agent 自己服務在上次執行之後的 journald 紀錄（`journalctl -u endpoint-agent --since`），找出 `Stopping`、`Main process exited, code=killed` 等訊息，記成 `os.service_stopped`。
- 不偵測系統紀錄被清除（見 §1.2）。

### 4.4 伺服器判定

| 事件組合 | 發現 |
|---|---|
| `agent.stopping`，`reason` 是 `service_stop` | `agent_stopped`（中） |
| `agent.stopping`，`reason` 是 `shutdown`、`upgrade` | 無 |
| `agent.started` 的 `clean` 是 false，而且期間沒有開機紀錄 | `agent_killed`（高）。從 `last_alive` 到啟動之間 |
| `os.service_stopped` 的 7034 | `agent_killed`（高） |
| `agent.service_config` 的 `to` 不是 `auto` | `agent_disabled`（高） |
| `os.log_cleared` | `log_cleared`（高） |

「期間沒有開機紀錄」：`agent.started` 時回報的開機時間晚於 `last_alive`，表示電腦重開或斷電，不算被強制結束。

## 5. C 層：網路端交叉比對

需要第 1 項（網路設備）的資料。只比對**跟裝置同一個據點**的網路設備，避免不同據點使用相同私有網段造成誤判。比對在伺服器每 5 分鐘執行一次（跟 MAC 表的查詢間隔相同）。

### 5.1 Agent 不報到，但電腦還在網路上（`silent_on_network`）

- **條件**：
  - 裝置超過「報到間隔 × 3，至少 5 分鐘」沒有報到。
  - 這段期間，交換器的 **MAC 表**在端點埠上看到這台裝置的 MAC，而且連續 3 次查詢（約 15 分鐘）都看得到。
- **只看 MAC 表，不看 ARP 表**：交換器的 MAC 表大約 5 分鐘沒流量就會清掉，代表電腦真的還在送封包。路由器的 ARP 表會保留好幾個小時，電腦關機後還會留著。
- **結束**：Agent 恢復報到，或交換器上看不到了。
- **細節**：交換器與埠、第一次與最後一次看到的時間。

**可能的誤判**：電腦睡眠時有些網卡仍會送少量封包（例如 Windows 的新式待命）。所以要求連續 15 分鐘，並且在說明裡提示這種可能。

### 5.2 IP 被別的 MAC 使用（`ip_conflict`）

- **條件**：
  - 裝置最近 10 分鐘內有報到，回報的 IP 包含 P。
  - 同據點路由器的 ARP 表裡，P 對到的 MAC 不屬於這台裝置，而且連續 2 次查詢都是這樣。
- **意義**：有人用了這台電腦的 IP（例如設定靜態 IP 冒充），或 Agent 回報的 IP 不實。
- 不做反方向（電腦的 MAC 在 ARP 表對到 Agent 沒回報的 IP）：ARP 表保留太久，DHCP 換過 IP 後舊的紀錄還在，會一直誤判。

### 5.3 同一個 MAC 出現在兩個埠（`mac_duplicate`）

- **條件**：這台裝置的某個 MAC，在同一次查詢中出現在兩個不同的**端點埠**（上行埠不算），連續 2 次查詢都是這樣。
- **意義**：有另一台設備複製了這台電腦的 MAC（例如想通過以 MAC 認證的網路）。
- 筆電換位置時，舊的埠會在 MAC 表過期（約 5 分鐘）前短暫重疊，所以要求連續 2 次。

## 6. E 層：序號缺口與日誌重建

沿用先前草稿的設計：

- **正常的缺口**：日誌超過上限刪掉最舊的未確認事件，或寫到一半斷電略過壞掉的行，Agent 都會記一筆 `journal.dropped` 說明筆數（壞行是新增的，`reason: "corrupt"`）。
- **伺服器**：
  - `device_journals`（裝置、日誌 ID、已收到的最大序號、還沒抵銷的說明筆數）。
  - 收到事件時，序號跳號就記缺口，再用 `journal.dropped` 的筆數抵銷。說明可能晚幾批才到，所以「缺了幾筆」與「說明了幾筆」分開累計。
  - 重新註冊沿用同一份日誌時，從原本的序號接續，不算缺口。
- **發現**：
  - 抵銷後仍有缺口：`journal_gap`，說明缺的序號範圍。
  - 30 天內出現 3 份以上不同的日誌 ID（第一份不算）：`journal_rebuilt`。

## 7. 後台

- **裝置頁「需要處理」**：每筆還沒確認的發現一項，標示嚴重度，點開看細節與「確認」按鈕。
- **裝置頁新分頁「完整性」**：全部的發現（含已確認的），與 Agent 啟動、停止紀錄。
- **時間軸**：每筆發現一筆，例如：
  - 「Agent 服務被停止（使用者 CORP\王小明）」
  - 「Agent 停止回報 42 分鐘，但台中 2F 交換器 Gi1/0/6 一直看得到這台電腦」
  - 「安全性紀錄被清除（CORP\王小明）」
- **裝置清單**：篩選「有完整性警示」。
- **總覽「需要處理」**：有高嚴重度、還沒確認的發現的裝置數。
- **網頁說明**：說明每種發現的意義、可能的正常原因、偵測不到的情況。

## 8. 保存

- `device_findings` 保存 365 天，跟多重連線紀錄相同。發現是稽核用的證據，比事件本身（180 天）留久一點。
- `device_journals` 跟著裝置；裝置刪除時一起刪。

## 9. 相容性

- 新事件種類用字串，舊版伺服器會照常存下、不處理。
- 舊版 Agent：沒有 A、B、D 層，也沒有記壞行的 `journal.dropped`（斷電造成的缺口會被標成 `journal_gap`，很少見，README 註明）。C 層不需要 Agent 配合，舊版也有效。
- 上線前已存下的事件不回頭檢查。已在追蹤的日誌從現有的最大序號接續。

## 10. 分期

1. **A 層與 E 層、發現的資料表與後台**：立即上傳、`journal.dropped` 壞行、序號缺口與日誌重建、發現的顯示與確認。
2. **B 層與 D 層**：Agent 啟動與停止事件、正常結束標記、服務啟動類型、Windows 系統紀錄訂閱、Linux 讀 journald。
3. **C 層**：網路端的三種比對。

每期各自一個 PR，各期都能單獨上線。

## 11. 測試

- **伺服器單元測試**（純函式）：
  - 缺口計算與抵銷：連續、跳號、重送、補號、說明晚到。
  - B 層判定：停止原因、非正常結束與重新開機的分辨、啟動類型。
  - C 層判定：連續次數、同據點限制、上行埠排除、恢復報到後結束。
- **整合測試**：
  - 立即上傳端點：驗證、批次上限、速率限制、與報到重複送出不會重複存。
  - 每種發現都會出現在裝置頁、時間軸、裝置清單篩選；確認後從「需要處理」消失並寫入稽核記錄。
  - C 層用直接寫入的 MAC 表、ARP 表資料測試。
- **Agent**：
  - 正常結束標記與 `last_alive`。
  - 停止前送出（模擬伺服器）。
  - Windows 事件訂閱的篩選與書籤（解析用的純函式；實際訂閱在 Windows CI 上跑一個寫入測試事件的整合測試）。
  - 壞行產生 `journal.dropped`。
